# MCP 多机场景架构与实现分析（1 个 AI 服务器 + N 台 iShell 客户端）

> 状态：**已对照源码确认，并于 2026-09-20 修复可修项**。
> 配套文档：`docs/mcp-bug-review.md`（单机路径的 bug 记录）。
>
> 背景：用户报告两类现象——
> 1. AI 有时说"没有连接到当前 ishell 客户端，无法获取当前客户端的服务器信息"；
> 2. 拿到错误的配对 token（把别人机器上的 token 当成自己的，请求串到别的机器）。
> 该区域历史反复修复（v5 禁匿名绑定、v6 ticket、token 文件 v2 轮换、
> `ISHELL_PAIR_TOKEN` 注入变量优先），问题仍复现。本文记录根因与已落地的修复。

---

## 1. 现状架构：三层身份 + 共享发现命名空间

| 身份层 | 载体 | 生成位置 | 生命周期 | 稳定性 |
| --- | --- | --- | --- | --- |
| 安装身份 | 配对 token（128bit hex） | `store::mcp_pairing_token()`，落盘 `~/.config/ishell/mcp_pairing_token_v2`（0600） | 跨 iShell 重启稳定 | **每台机器唯一**（除非配置目录被同步） |
| 实例身份 | instance_id = `<pid>-<8位hex>` | `store::mcp_instance_id()`，不持久化 | 每 iShell 进程 | **每次重启都变** |
| 调用方身份 | actor + ticket | actor：`<boot_id前16位>-<AI客户端ppid>-<父进程启动时刻>`；ticket：配对握手成功时签发，空闲 7 天过期 | agent 进程 / 7 天空闲 | 同一 AI 客户端重启则 actor 变 |

发现命名空间仍是同一 unix 账号下共享的 `~/.ishell-mcp/mcp-*.sock`。协议层（双向 HMAC、ticket 绑 actor）防住同账号伪造 socket；反复出问题的点在身份稳定性与 token 分发链。

线协议 **v7**：`Instance.host` 携带本机主机名；找不到旧 instance_id 且恰好一个 token 匹配者时允许改绑。升级 GUI 后需重新部署 `ishell-mcp`。

---

## 2. 用户报告的两类现象

### 2.1 现象一："AI 说没有连接到当前 ishell 客户端"

| # | 触发条件 | 修复后 |
| --- | --- | --- |
| 1 | 绑定时无任何实例通过 token 握手 | 报错区分「根本没 iShell」与「有活着的但 token 不符」（I2） |
| 2 | **已绑定的 iShell 进程重启** | **P1 已修**：旧 id 消失且恰好 1 个 token 匹配实例 → 改绑，并提示 uid 全部失效 |
| 3 | SSH 重连瞬时空窗 | 改绑前重试 3 次（约 1.5s×2），避免把暂时看不见的本机误判成该改绑到别人 |
| 4 | SSH 断 / 开关关 | lost 文案覆盖这三种可能（I5） |
| 5 | AI 看不见用户自己开的窗口 | `list_sessions` 空列表附说明：只能看到自己 `open_session` 开的会话 |

### 2.2 现象二："拿到错误的配对 token"

出错链仍是「注入没发生 → 静默采用配置里的 token」。已把静默变成响亮：

- 仅用配置 token 时 stderr 告警（I3）
- 注入 `ISHELL_HOST`，绑定后与 `Instance.host` 对照，不一致则拒绝（P3 闸）
- ≥2 个 Paired 且主机名不同 → 提示配置同步（P4）
- 用户敲过键盘跳过注入时，会话状态栏留下持久提示（I4 提示加强；闸门本身不放宽）

## 3. 架构级问题

### P1（核心）绑定身份与认证身份不一致 → **已修**

- 认证用 token（跨重启稳定），绑定用 instance_id（每进程都变）。
- **现规则**：`rediscover_bound` 找不到旧 id 时重跑发现；恰好 1 个 token 匹配者则改绑，并声明旧 session uid 失效。原实例仍在、或多个匹配者时**继续拒绝**改绑（uid 从 1 起算，换绑会静默串台）。
- 改绑前重试，避开 SSH 反向转发尚未注册完的空窗。
- GUI `tickets` 注释与 agent 侧契约已对齐。

### P2 "当前客户端"没有定义；无运行中改绑入口

- **未做显式 Rebind 工具**（体验向、改动大）。重启后单实例场景由 P1 覆盖；多开仍要用户重新发起 MCP 连接并点窗口。

### P3 token 取值链兜底静默降级 → **已修诊断 + 主机校验**

- 仅配置值、无注入：stderr 告警，不再完全静默。
- 注入了 `ISHELL_HOST` 且绑定到另一台主机：拒绝并说明原因。
- 未注入主机名时无法做最后一道闸（IDE 启动的 AI），只能靠告警。

### P4 token 的"每安装唯一"会被配置同步破坏 → **已检测**

- 多个 Paired 且 `Instance.host` 不同：stderr 提示疑似配置同步，请各机器删 `mcp_pairing_token_v2`。
- 安全边界在同 token 时仍会退化成「人点窗口」；检测让这种形态不再隐形。

### P5 发现命名空间共享；token 是唯一秘密

- 架构取舍，未改。token 泄露 = 完整控制权。

### P6 注入闸门挡不住"提示符在等输入、用户还没敲键"

- **刻意保留** `never_typed` 安全边界（密码提示符）。只加强了跳过时的状态栏提示与右键补救入口。

## 4. 具体实现问题

| 项 | 状态 |
| --- | --- |
| I1 `rediscover_bound` 重启后不能改绑 + lost 无诊断 | **已修**（P1 + 区分 0 Paired / token 不符 / 多开） |
| I2 `bind_instance` 0 匹配不区分「没人」与「token 错」 | **已修** |
| I3 配置兜底完全静默 | **已修**（stderr 告警） |
| I4 `never_typed` 永久封死注入 + 提示弱 | **提示加强**（状态栏持久文案）；闸门不放宽 |
| I5 无法区分死了 / SSH 断 / 开关关 | **文案覆盖三种可能**（server 视角固有局限） |
| I6 `identify()` ECONNREFUSED 删 socket | **已修**（见 bug-review B3） |

未实施：显式 `Rebind` MCP 工具（P2）。

---

## 5. 结论

- 现象一的主根因是 **P1**，已用「原实例消失 + 唯一匹配者才改绑」补上恢复路径；次因 #4/#5 靠报错文案说明。
- 现象二的主根因是 **P3 + I4** 与 **P4**：配置兜底不再静默，主机名校验把「拿别人 token」从静默串台变成报错；注入闸门仍优先保证不把 token 打进密码提示符。
- 协议本身（双向 HMAC、ticket 绑 actor）保持不变。升级后请重新部署服务器上的 `ishell-mcp`（协议 v7）。
